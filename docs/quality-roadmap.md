# Роадмап: регламент качества для Rezka TV

Исходники: «Инженерный регламент» и правила тестов «Angry Tests» (главы 2, 3, 6) — адаптированы под Android TV-клиент.
Каждый PR ≤ 200 строк и ≤ 10 файлов; тесты, фикстуры, снимки и журналы долга `quality/*-baseline.*` не считаются.

## Решения владельца (2026-10-24)
1. Правила тестов строго для всех тестов, включая старые: один assert последним, ≤ 12 строк, без литералов в assert,
   сообщение в каждом assert, без setUp/tearDown, без констант в тестах, имена — предложения с глагола.
2. Тесты по-настоящему недетерминированные: случайные данные, новый seed на каждый прогон; seed печатается
   при падении, повтор — `./gradlew test -Pseed=…`; ночное падение → issue с seed → агент пишет регрессионный тест.
3. Полный запрет комментариев везде, включая `proguard-rules.pro` и XML: код пишет ИИ, комментарии ему мешают.
4. Производительность — калибровка: одни и те же бенчмарки на раннере GitHub и на ТВ, коэффициент на каждый
   бенчмарк, CI прогнозирует время на ТВ и блокирует выход за бюджет; финальный замер на ТВ перед релизом.
5. GUI-тесты: Espresso на эмуляторе Android TV API 28 (KVM на раннерах GitHub), фейковый rezka-сервер
   на эфемерном порту с фикстурами; проверяются D-pad, фокус, «Назад».
6. SpotBugs + find-sec-bugs: один пробный прогон на текущем коде, решение — по числу ложных срабатываний.
7. ZAP: `LoginServer` на JVM в CI на эфемерном порту, сканирование из docker; плюс фаззинг разбора запросов.
8. Облачные и прочие инструменты: SonarCloud (Kotlin, токен), OSV-Scanner (уязвимости зависимостей),
   LanguageTool (русский: `strings.xml`, документация), typos (идентификаторы), ORT + reuse-action (ночью),
   randoop на байткоде `:core` (поиск падений, сгенерированное не коммитится).
9. ИИ-агенты на DeepSeek через Anthropic-совместимый API (секрет `DEEPSEEK_API_KEY`, модель `deepseek-flash`; с 2026-10-25): триаж, ревью PR по регламенту,
   master-fixer, issue по нестабильным тестам.
10. pitest ≥ 85 % для всего кода: логика выносится из Activity в `:core`, Activity — тонкие (не Robolectric).
11. Разбиение `PlayerActivity` — делаем, PR плеера владелец проверяет вручную.

## Фазы
- Ф0. `./gradlew verify`, размер PR, ruff, предупреждения = ошибки, workflow. — смержено (PR #1, 9ff3faf).
- Ф1. Запрет комментариев во всех файлах — проверка `tools/gates/comments.py` и журнал `quality/comments-baseline.txt`
  смержены (PR #15–#17, #20); идёт чистка журнала пачками по ≤ 10 файлов, `rezka/player` и `rezka/login` — отдельными PR
  на ручную проверку; тесты остаются в журнале до перевода в Ф2 — их комментарии становятся именами тестов.
  Дальше: `ruff format`, typos, detekt+ktlint (с журналом), раскладка файлов (один верхнеуровневый
  класс на файл, имя файла = имя класса, пакет = каталог, тест зеркально исходнику).
- Ф2. Тестовая дисциплина: JUnit 5, Hamcrest (Kotlin и PyHamcrest), maybeslow, таймауты, параллельность,
  fast ≤ 100 мс / `@Tag("deep")`, тишина лога, tmpdir доступен после прогона, без сети; проверка правил тестов
  (2.x, 3.x) скриптом и по диффу (нельзя удалять `@Test`, изменение кода требует тестов); `:testkit` — матчеры,
  фейки, генераторы, DSL; снимки; перевод всех старых тестов (Kotlin и Python).
  Долг описан в issue #14.
- Ф3. Модуль `:core`, вынос логики из Activity, ArchUnit, правило detekt для аргументов по умолчанию (3.29).
- Ф4. Контракты: JSON Schema хранимых данных и протокола входа, снимки разбора, диф и метка `contract-break-approved`.
- Ф5. Безопасность и лицензии: Lint security, CodeQL, пробный SpotBugs, OSV-Scanner, SonarCloud, REUSE, Renovate.
- Ф6. Эшелон 2: release + размер APK, deep-тесты, потокобезопасность на всех ядрах, Kover, CPD, LanguageTool,
  Playwright для страницы входа (Chromium, WebKit, Firefox), Espresso на эмуляторе.
- Ф7. Ночью: pitest ≥ 85 %, jqwik с большим числом попыток, Jazzer, randoop, JMH + калибровка под ТВ,
  github-action-benchmark, живой smoke против rezka, ZAP, ORT.
- Ф8. `tools/release.sh`: установка на ТВ, health check (старт < 1 с, gfxinfo, logcat), сравнение с прошлым релизом, откат.
- Ф9. Агенты: Impact-отчёт и оценка риска, триаж, master-fixer, issue по нестабильным тестам, автомерж.
  ИИ-ревьюер работает (PR #2–#5, #35, #37–#40): `.github/ai-review.md`, обязательная проверка `ai-review`, помнит свои
  прошлые замечания, не повторяется на том же диффе; сканер техдолга завёл issue #8–#14.
- Ф10. CLAUDE.md под регламент.

## Открытые вопросы
1. Автомерж включён (решение владельца 2026-10-25): агент включает автослияние при открытии PR, кроме PR с меткой «ручная проверка». Защита `main`: `verify` и `ai-review`; закрытие обсуждений не требуется (см. «Ослабления после пробы»).

## Ослабления после пробы (2026-10-25)
Регламент в исходном виде проверен на этом проекте за день: ~30 PR, ИИ-ревью одним запросом на DeepSeek Flash.
Настоящие находки ревью (около десятка: падение гейта на двоичном файле, тест, не проверявший проверку кривой,
повторная публикация старого вердикта, перепутанный порядок входов запроса) почти все пришли в первом-втором
раунде. Дальше раунды шли на полировку строк логов и текстов в служебных скриптах — 4 раунда на PR, одна задача
дробилась на 6 PR. В команде с людьми такое начнут обходить: тесты ради галочки, искусственное дробление PR.
Поэтому для переноса в проект с людьми ослаблено:
1. **Правило 3 ревью по областям.** Код приложения — строго: тест должен падать при поломке изменённой строки.
   `tools` и CI — блокирует только изменение поведения вообще без теста. Логи, диагностика, тексты и заголовки
   без отдельного теста не блокируют.
2. **Блокируют только блокирующие замечания.** Требование «все обсуждения закрыты» в защите `main` снято;
   блокирующие и так держат PR через проверку `ai-review`, неблокирующие — советы автору.
3. **Тесты не входят в предел 200 строк** (`tools/gates/pr_size.py`): хороший тест не должен заставлять делить PR.

Жёстким осталось дешёвое и механическое: комментарии, форматирование, линтеры, правила тестов, размер кода,
зелёные тесты, отчёт в PR.
